# 변경 안전성 체크리스트

기능 수정 뒤에 생길 수 있는 오류, 설계 모순, 상태 꼬임, 고아 UI, 반응형 훼손을 배포 전에 찾기 위한 공통 점검표입니다. 작은 수정은 관련 항목만 적용할 수 있지만, 데이터 모델·화면 흐름·공용 레이아웃·삭제 동작을 바꾼 경우에는 전체 항목을 확인합니다.

프로젝트 로컬 [`$lore-studio-ui-safety`](../.codex/skills/lore-studio-ui-safety/SKILL.md)는 이 체크리스트와 `UI_PAGE_CONTRACT.md`를 함께 읽어 점검 범위와 증거를 구성합니다. 새 실패 유형·안전 경계·재현 가능한 검사법이 생기면 이 문서와 관련 테스트를 같은 변경에서 갱신합니다.

## 판정 규칙

- `[x]`는 실제 확인 또는 자동 검증 증거가 있는 항목에만 표시한다.
- 적용되지 않는 항목은 `[N/A — 이유]`로 기록한다. 확인하지 않은 항목을 N/A로 처리하지 않는다.
- 하나라도 데이터 손실, 권위 경계 위반, 저장 상태 불일치, 주요 동작 접근 불가가 발견되면 배포를 중단한다.
- 자동 테스트 통과만으로 UI 상태·스크롤·고정 바·취소 복원을 통과 처리하지 않는다. 실제 데스크톱과 모바일 화면을 확인한다.
- 최종 증거는 `VERIFICATION.md`에 남기고, 영구적인 UI 규칙은 `INFORMATION_ARCHITECTURE.md`에 반영한다.

## 1. 변경 범위와 기준선

- [ ] 사용자 요구를 기능, 화면, 데이터, 문서, 테스트 단위로 나눴다.
- [ ] 변경 전 정상 동작과 변경 후 기대 동작을 한 문장씩 기록했다.
- [ ] `git status`와 `git diff`로 사용자 작업이나 무관한 변경이 섞이지 않았음을 확인했다.
- [ ] 신규·수정 파일이 적절한 영역(`backend/app`, `frontend/src`, `schema`, `config`, `docs`)에 있다.
- [ ] 새 기능에 필요한 API, 스키마, migration, 테스트, 문서 갱신 범위를 확인했다.
- [ ] 기존 데이터가 있는 환경과 빈 데이터 환경에서 기대 결과를 각각 정의했다.
- [ ] 변경한 화면을 `UI_PAGE_CONTRACT.md`의 페이지 골격·스크롤 소유권·상태 표현과 비교했다.

## 2. 불변 설계와 데이터 경계

- [ ] 컨셉 본문, 집필 지침, 전개 방식, 문체 프로필, 출력 설정을 하나의 만능 프롬프트 필드로 합치지 않았다.
- [ ] AI 결과는 `CANDIDATE`이며 사용자 승인 없이 `PROJECT_CANON`이나 저장 본문이 되지 않는다.
- [ ] 세계관 자료의 자유 본문이 중심이고 빈 구조화 필드를 강제하지 않는다.
- [ ] 작문 참고 예시의 사실이 프로젝트 설정이나 정식 근거로 유입되지 않는다.
- [ ] 생성 실행에 모델, 입력 선택, 시드, 레시피·프로필 버전, 출력 설정이 기록된다.
- [ ] 장문 입력은 컨텍스트 컴파일러를 거치며 사실·질문·금지·참고 역할이 분리된다.
- [ ] 생성 오류나 미승인 제안을 다음 실행의 사실로 재사용하지 않는다.
- [ ] 전개 방식은 정보 공개 순서와 수사적 이동을 표현하며 소재별 목차로 퇴행하지 않는다.
- [ ] 모델 호출은 OpenAI 호환 게이트웨이를 경유하며 도메인 코드가 특정 런타임에 결합하지 않는다.
- [ ] 역할별 모델 연결 API는 키 원문을 응답·감사 로그에 남기지 않고, 저장 전 `/v1/models`와 alias를 시험하며, 앱 저장값 삭제 뒤 `.env`로 복귀한다.
- [ ] 프로젝트 ID와 소유권 검사가 모든 조회·연결·생성 입력에서 유지된다.

## 3. 코드 오류와 꼬임

- [ ] 충돌 표식(`<<<<<<<`, `=======`, `>>>>>>>`)과 임시 `TODO/FIXME/HACK`가 남지 않았다.
- [ ] 사용하지 않는 import, 변수, 함수, CSS class, 이벤트 핸들러가 남지 않았다.
- [ ] 같은 상태를 여러 변수·스토어·DOM 속성이 서로 다르게 소유하지 않는다.
- [ ] 화면 표시용 값은 가능한 한 한 원본 상태에서 파생하며 수동 복제 상태를 최소화했다.
- [ ] 취소용 snapshot은 배열·객체의 참조 공유로 인해 함께 변하지 않는다.
- [ ] 선택 변경 시 이전 미리보기, 글의 흐름, AI 결과처럼 더 이상 유효하지 않은 파생 상태가 초기화된다.
- [ ] 비동기 요청의 성공·실패·중복 클릭 후 `busy`, error, modal 상태가 반드시 정상 복구된다.
- [ ] 빠른 프로젝트 전환이나 항목 전환 뒤 늦게 도착한 응답이 현재 화면을 덮어쓰지 않는다.
- [ ] 새 서버 호출은 `frontend/src/lib/api.js`를 경유하며 URL·오류 처리가 화면마다 중복되지 않는다.
- [ ] API 삭제·수정은 ORM cascade와 DB FK 동작이 일치하며 bulk 작업이 필요한 이유가 코드에 드러난다.
- [ ] 반복 조건이나 레이블이 서로 다른 화면에 복사되어 불일치하지 않는다.
- [ ] 임시 로그, 디버그 출력, 테스트 전용 분기, 고정된 테스트 ID가 제품 코드에 남지 않았다.

## 4. 화면 상태와 이동 흐름

각 주요 흐름에서 `진입 → 변경 → 취소 → 재진입 → 저장 → 새로고침 → 프로젝트 전환 → 복귀`를 확인합니다.

- [ ] 최초 진입 상태가 의도한 읽기·선택·진행 단계와 일치한다.
- [ ] 수정 버튼은 해당 입력을 열고, 저장은 읽기 상태 또는 다음 명시 단계로 복귀한다.
- [ ] 취소는 서버 저장값과 수정 전 선택을 정확히 복원한다.
- [ ] 확인 화면의 `수정`은 일반 단계 진행으로 바뀌지 않고 `확인·작성으로 돌아가기`를 제공한다.
- [ ] 수정 완료와 수정 취소가 각각 변경 유지와 원상 복원으로 명확히 구분된다.
- [ ] 입력 변경으로 기존 생성 결과가 무효가 되면 사용자에게 다시 확인해야 함이 화면에 드러난다.
- [ ] 브라우저 새로고침 뒤 저장된 상태는 유지되고 임시 입력은 저장된 것처럼 보이지 않는다.
- [ ] 브라우저 뒤로 가기·직접 URL 진입에도 빈 프레임이나 잘못된 단계가 나타나지 않는다.
- [ ] 프로젝트 전환 시 이전 프로젝트의 선택, 검색, modal, 자료, AI 결과가 남지 않는다.
- [ ] 목록의 마지막 항목 삭제 후 안전한 빈 상태 또는 다음 항목을 선택한다.
- [ ] 오류 후 재시도할 수 있고, 오류 메시지가 성공 메시지와 동시에 남지 않는다.

## 5. 생성·조회·수정·삭제 일관성

- [ ] 생성 직후 목록, 상세, 선택 상태가 같은 객체를 가리킨다.
- [ ] 수정 저장 뒤 목록 카드와 상세 읽기 화면이 함께 갱신된다.
- [ ] 저장하지 않은 수정은 목록·다른 화면·LLM 입력에 반영되지 않는다.
- [ ] 삭제 확인문에 정확한 이름, 영향 범위, 되돌릴 수 없음이 표시된다.
- [ ] 프로젝트 삭제는 소유 자료·세션·원고·로어북을 제거하고 감사 묘비는 보존한다.
- [ ] 세계관 자료 삭제는 관계·리비전·인덱스 등 종속 데이터 처리와 일치한다.
- [ ] 로어북 삭제는 출처 초안을 보존한다.
- [ ] 삭제 성공 후 목록, 현재 선택, 로컬 저장 프로젝트 ID가 고아 ID를 참조하지 않는다.
- [ ] 삭제 실패 시 화면에서 먼저 사라지거나 성공 메시지를 표시하지 않는다.
- [ ] 이미 삭제된 항목, 다른 프로젝트 항목, 사용 중이라 삭제할 수 없는 항목의 API 오류가 이해 가능한 UI로 전달된다.
- [ ] destructive API는 감사 기록을 남기며 기록 자체가 부모 삭제 cascade로 사라지지 않는다.

## 6. 고아 UI 검사

- [ ] 주요 메뉴의 모든 항목이 실제 내용이 있는 페이지로 연결된다.
- [ ] 페이지 제목, 탭, 카드, 도움말에서 더 이상 존재하지 않는 기능을 안내하지 않는다.
- [ ] 버튼·링크마다 클릭 결과가 있으며 비활성 버튼에는 비활성 이유가 있다.
- [ ] 생성·수정 modal마다 닫기, 취소, 저장 경로가 모두 존재한다.
- [ ] 빈 `page-tools`, 빈 header, 빈 카드 footer, 설명만 남은 패널이 공간을 차지하지 않는다.
- [ ] 읽기 모드에서 편집 toolbar나 비활성 입력이 유령처럼 남지 않고, `글 편집` 진입점은 보인다.
- [ ] 삭제·이름 변경 뒤 깨진 링크, 빈 이미지, 존재하지 않는 badge·필터 값이 남지 않는다.
- [ ] 목록 필터 결과가 0개일 때 빈 상태와 필터 해제 방법을 알 수 있다.
- [ ] 로딩·빈 데이터·API 오류·오프라인 상태가 서로 구별된다.
- [ ] hover에만 의존하는 핵심 동작이 없으며 tooltip은 클릭·키보드로도 확인할 수 있다.

## 7. 레이아웃 훼손과 반응형

최소 desktop `1600×900`, mobile `390×844`, 좁은 mobile `360×844`에서 확인합니다.

- [ ] 브라우저 전체가 불필요하게 스크롤되지 않고 각 작업면이 의도한 내부 스크롤을 소유한다.
- [ ] 내부 스크롤 영역에 `min-height: 0`과 올바른 flex/grid 제약이 적용된다.
- [ ] 고정 하단 이동 바가 전역 메뉴, `자료 더 보기`, modal footer를 가리지 않는다.
- [ ] `자료 더 보기`는 카드 목록과 전역 단계 이동 사이에서 고정되며 서로 겹치지 않는다.
- [ ] 카드 grid 행이 콘텐츠 높이 때문에 겹치거나 비정상적으로 수축하지 않는다.
- [ ] sticky 요소가 부모 `overflow` 때문에 작동을 잃지 않는다.
- [ ] tooltip과 modal이 다른 패널의 overflow 또는 z-index에 잘리지 않는다.
- [ ] 긴 한국어 제목·태그·버튼 문구가 카드 폭을 늘리거나 가로 스크롤을 만들지 않는다.
- [ ] 이미지 없음·세로 이미지·긴 이미지 data URL에서도 카드 비율과 fallback이 유지된다.
- [ ] 좌측 패널 접힘·펼침 뒤 본문 폭과 고정 요소 위치가 다시 계산된다.
- [ ] 모바일 하단 메뉴 위로 핵심 버튼과 마지막 입력 필드가 충분히 노출된다.
- [ ] 모바일 우측 고정 `모델 연결` 링크가 page-tools의 마지막 버튼·테마·프로젝트 조작을 가리거나 pointer event를 가로채지 않는다.
- [ ] 실제로 스크롤되지 않는 모바일 자식에 `overscroll-behavior: contain`을 두어 부모 문서 제스처를 차단하지 않는다.
- [ ] 모바일 AI 패널의 긴 선택 문장·pre·input이 flex/grid min-content 폭으로 편집기와 문서 폭을 늘리지 않는다.
- [ ] 모바일에서 입력·submit을 자동 scroll/focus한 후 `elementFromPoint`가 하단 메뉴가 아니라 해당 조작을 가리킨다.
- [ ] 360px command bar에서 프로젝트 선택·생성이 한 행, 글 만들기는 5+4 두 행, 원고 작업은 3칸 한 행을 유지한다.
- [ ] 1개, 18개, 19개, 73개 자료에서 카드·더 보기·스크롤이 모두 정상이다.
- [ ] CSS `:has`, `color-mix`, sticky 등 사용 기능이 지원 대상 Chromium에서 실제 동작한다.

## 8. 시각·접근성 손상

- [ ] 선택, 진행 중, 완료, 오류, 비활성 상태가 색상 하나에만 의존하지 않는다.
- [ ] 시작 전 단계가 완료 녹색으로 보이지 않고 실제 성공 후에만 완료 표시된다.
- [ ] 진녹색·남색 배경의 본문과 AI 제안 텍스트가 아이덴티티 금색 또는 충분한 명도 대비를 가진다.
- [ ] 읽기 본문의 글자 크기, 줄 길이, 행간이 입력 form보다 우선되어 보인다.
- [ ] 포커스 표시가 보이고 Tab 순서가 화면의 읽기 순서와 일치한다.
- [ ] icon-only 버튼에 `aria-label`이 있고 현재 탭·단계·선택에 올바른 ARIA 상태가 있다.
- [ ] dialog는 제목을 가지며 열렸을 때 배경 조작이 차단되고 닫은 뒤 합리적인 위치로 포커스가 돌아간다.
- [ ] 이미지에 의미 있는 대체 텍스트가 있으며 장식 이미지는 보조 기술에서 제외된다.
- [ ] 브라우저 console error, page error, 실패한 필수 API 요청이 없다.

## 9. AI 기능 회귀

- [ ] AI 요청의 자유 입력·연결 ID·경계 목록을 프론트에서 API 스키마의 형식·개수·길이 제한에 맞게 검증하며, 422 검증 오류는 실패한 필드와 제한을 화면에 보여 준다.
- [ ] Tiptap/ProseMirror 본문의 첫 위치부터 전체 선택한 AI 수정은 `selection_from=0`을 정상 좌표로 받아들이고, 제안 반영 전까지 저장 본문을 바꾸지 않는다.
- [ ] AI 수정은 전체 본문과 선택 범위, 필요한 앞뒤 문맥을 구분해 전달한다.
- [ ] AI 작성은 사용자가 고른 연결 자료만 실행 입력으로 사용한다.
- [ ] 세계관 본문의 AI 수정·AI 작성에서 선택한 Qwen/Gemma가 해당 요청·제안 표시·GenerationRun의 model/endpoint/model_key와 일치하고 다른 모델로 fallback하지 않는다.
- [ ] 선택하지 않은 프로젝트 자료와 작문 참고 예시의 사실이 결과 근거로 섞이지 않는다.
- [ ] 결과는 비교 가능한 제안으로 표시되고 `반영` 전 DB가 변하지 않는다.
- [ ] 취소·닫기·새 실행 뒤 오래된 제안이 현재 본문에 적용되지 않는다.
- [ ] `더 자세히` 등 길이 의도가 토큰 예산과 출력 계약에 실제 반영된다.
- [ ] 모델 오류, timeout, 잘못된 구조화 응답에서 편집 중인 사용자 본문이 보존된다.
- [ ] GenerationRun에 사용된 입력·버전·모델·파라미터가 재현 가능한 수준으로 남는다.
- [ ] 자료 양산은 기획 에이전트 1개가 6–30개의 서로 다른 `제목 + 간단한 내용` 씨앗만 만들고 이 단계에서 ConceptPage를 저장하지 않는다.
- [ ] 사용자가 고른 씨앗만 본문 호출을 시작하며 선택 자료 수 1–10개와 별도의 최대 동시 작업 수 1–10개를 각각 지킨다.
- [ ] 자료 양산의 기본 경로는 `Qwen 씨앗 기획 / Gemma 본문 집필 / 최대 동시 작업 4개`를 자동 적용하고, 모델·동시성 변경은 접힌 고급 설정에서만 노출한다.
- [ ] 씨앗과 본문은 각각 명시된 Qwen 또는 Gemma 프로필을 사용하며, 참고 자료 한 개·자료 종류 한 개와 동일한 스냅샷 문맥을 유지하고 역할 fallback으로 다른 모델에 넘어가지 않는다.
- [ ] 씨앗은 차별점·참고 근거를, 본문은 종류별 핵심 항목·계승 사실·새 설정 후보·실제 글자 수를 반환하며 이 품질 정보가 저장 후보의 생성 이력에 남는다.
- [ ] 일부 병렬 작업 실패는 다른 성공 결과를 버리지 않고 seed별 실패를 GenerationRun과 UI에 표시한다.
- [ ] 완성 결과는 선택 저장 전 DB를 바꾸지 않으며 저장 뒤에도 `CANDIDATE`이고, 같은 worker run을 중복 저장할 수 없다.

## 10. API·DB·문서 모순

- [ ] 프론트 요청 payload와 Pydantic 응답·요청 schema의 필드명과 nullable 조건이 일치한다.
- [ ] SQLAlchemy 모델, Alembic head, DB의 실제 FK·nullable·cascade가 일치한다.
- [ ] migration을 기존 데이터에서 `upgrade`하고 가능한 경우 임시 DB에서 `upgrade → downgrade → upgrade`했다.
- [ ] API가 사용하는 HTTP 상태 코드와 프론트 성공·오류 분기가 일치한다.
- [ ] 모델 설정 migration 뒤 기존 `.env` 프로필이 그대로 작동하며 Writer·Utility·Vision·Embedding override가 서로 격리되고, Writer·Utility·Vision은 Qwen·Gemma를 역할별로 독립 선택할 수 있다.
- [ ] README, DEVELOPMENT, DATA_MODEL, IMPLEMENTATION_STATUS, ACCEPTANCE_TESTS, VERIFICATION의 head·용어·테스트 수치가 서로 모순되지 않는다.
- [ ] 삭제·상태 전이·생성 입력처럼 장기 유지할 규칙이 문서와 코드 양쪽에 있다.
- [ ] 제거한 기능의 문구, schema, fixture, 테스트, 문서 참조가 남지 않았다.
- [ ] 현재 동작하지 않는 미래 계획을 완료 기능처럼 문서화하지 않았다.

## 12. 이번 UI 변경 집중 회귀

- [ ] 결과물 형태의 형식·시점·시제·분량을 바꿀 때 원고 견본 네 줄이 즉시 갱신된다.
- [ ] 결과물 견본의 원고 설계 장부에 주제·배경·주요 요소·갈등·변수·집필 지침·전개 방식·문체·필력이 앞 단계의 실제 선택과 일치하고, 미선택 항목은 `선택 안 함`으로 표시된다.
- [ ] 확인·작성에서 소재를 수정하고 완료하면 확인 화면으로 돌아간다.
- [ ] 확인·작성에서 소재를 바꾸고 취소하면 원래 선택이 복원된다.
- [ ] 집필 원칙·전개 방식·문체·출력 설정도 같은 edit-and-return 규칙을 따른다.
- [ ] 글의 흐름·초안은 실행 전 녹색이 아니며 각 성공 뒤 순서대로 완료된다.
- [ ] 확인·작성 왼쪽에는 결과물 형태와 같은 전체 원고 설계 견본이 유지되고, 오른쪽 한 결과 영역은 흐름 카드 클릭 시 흐름으로, 초안 카드 클릭 시 초안으로 교체된다.
- [ ] 확인·작성은 `글의 흐름 설계 → 초안 작성`만 사용자 단계로 보여 주고 자료 경계 컴파일을 별도 중복 단계로 노출하지 않는다.
- [ ] 결과물 형태에서 정한 기본·직접 지정 분량과 생성된 글의 흐름 문단 예산 합계가 일치한다.
- [ ] 모든 분량 선택은 계획 예산뿐 아니라 저장 직전 실제 한국어 글자 수도 목표의 95% 이상인지 검사한다.
- [ ] 6,000자 미만 Writer·Finalizer는 목표에서 `max_tokens` 안전 상한을 계산하고, 조기 종료 시 결말 뒤가 아니라 마지막 문단 직전에 새 사실·고유명·원인·미래 정보 없는 보강 문단을 최대 세 번 삽입하며, 그래도 95%에 미달한 결과는 저장하지 않는다.
- [ ] 6,000자 미만 결과가 목표를 넘어도 앞부분 글자 수로 기계적 절단하지 않으며, 필수 귀결·반복 신호·마지막 이미지를 보존한다.
- [ ] 장문 Writer·Finalizer는 전개 구간별 이어쓰기로 부족분을 채우고 호출 수·목표·실제 글자 수를 GenerationRun에 남기며, 심한 미달 결과를 성공으로 저장하지 않는다.
- [ ] 장문 이어쓰기의 동일·유사 문단을 생성 중과 저장 직전에 차단하고, 결론이 짧을 때 같은 종결문 대신 계획 대비 부족한 분석 구간을 보충한다.
- [ ] `선택 자료 본문 반영`은 선택 자료에만 적용되고, 선택 자료가 0개인 API 입력에서는 `core`로 비활성화된다.
- [ ] 소설·수필·보고서용 공용 전개 방식·문체 프로필·결과물 형태가 프로젝트와 무관하게 보이며 공용 문체는 읽기 전용이다.
- [ ] 세계 내부 구술은 화자의 목격·전언·추측과 지식 범위를 유지하고, 메타 설명 없이 완성 원고만 출력한다.
- [ ] 세계 내부 구술 자산에 전용 `max_tokens`나 고정 글자 수 규칙이 없고 기존 분량 선택과 GenerationRun 분량 계약을 그대로 사용한다.
- [ ] 자료 큐레이션·해설은 제공된 직접 인용만 사용하고 의역·해설·전체 종합을 구분하며, 없는 기록 번호·원문·출처를 만들지 않는다.
- [ ] 상징적 우화는 반복 신호의 물리적 특성을 고정하고 반응만 변화시키며, 선택하지 않은 근거·장면 이후 정보·상징 직접 해설·참고 작품의 고유 문구를 추가하지 않는다.
- [ ] Planner가 선택 자료에 없는 근거 ID를 만들면 서버가 이를 허용하지 않고 선택 근거로 복구하며 경고를 남긴다.
- [ ] 결과물 형태 선택 시 권장 생성 성향이 선택되고 `정밀 / 균형 / 표현 풍부`를 사용자가 다시 선택할 수 있다.
- [ ] 고급 샘플링은 온도·Top P·Top K·반복 억제·새 화제 허용의 범위만 받으며 최대 토큰·글자 수를 소유하지 않는다.
- [ ] Writer에는 선택/덮어쓴 샘플링 값이 적용되고 Planner는 구조화 안정용 고정값을 유지하며, Finalizer는 선택값에서 파생한 보수적 상한을 사용한다.
- [ ] GenerationRun과 원고 생성 입력에 생성 성향 key·version·실제 파라미터 snapshot이 남는다.
- [ ] 저장된 세계관 자료는 읽기 모드로 열리고 `글 편집` 뒤에만 입력과 AI 동작이 활성화된다.
- [ ] 자료 저장·취소 뒤 읽기 모드로 돌아오며 새 자료는 바로 편집할 수 있다.
- [ ] 프로젝트·세계관 자료·로어북의 삭제 확인문과 삭제 후 목록 상태가 정확하다.

- [ ] 로어북 `.page-tools` 왼쪽의 `노말 / 판타지아 / 메카니컬 / 어반 판타지` 원형 테마가 번호·이름·`aria-pressed`로 식별되고 새로고침 뒤에도 선택이 유지되며 책장 안에 중복되지 않는다.
- [ ] 로어북 테마 변경 전후 본문·프로젝트·생성 입력·내보내기 URL은 바뀌지 않으며 읽기/편집 전환과 저장·취소·삭제 동작이 그대로 유지된다.
- [ ] 네 로어북 테마 모두 desktop 1600px·mobile 390px·narrow 360px에서 본문·제목·입력란·버튼 대비와 가로 overflow를 통과한다.
- [ ] 판타지아는 밝은 양피지·굵은 적갈색, 메카니컬은 단순 선형 암부·형광 녹색·배경 한정 글리치, 어반 판타지는 공포 질감 없는 남색 도시 네온이라는 시각 역할을 유지한다.
